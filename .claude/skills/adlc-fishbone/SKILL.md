# AgentDLC 五维鱼骨图（workshop 版）

定义环的第一步：从一个具体的 Agent 场景出发，和**业务方**一起找出“什么会阻止这个 Agent 稳定上线”，画成一张五维鱼骨图。
图上只记录业务方**自己确认过的障碍**，不写方案。下一步用 `adlc-criteria` skill 把这些障碍翻译成判据和黄金样本。

**workshop 里的角色**：你是主持人；对面是一组学员，扮演业务方，按角色卡 `data/scenario/role-card.md` 回答（实验场景：企业软件平台的需求评审，样例平台是示例 CRM PaaS）。
他们也可以选用自己组的 Agent 场景（可选扩展），那时没有角色卡，按他们的真实经验回答。

> 改编自 AgentDLC v-Team 的 agent-dlc-fishbone skill（同一套五维问法、同一个 drawio 模板和 JSON 结构）。
> 模板：本 skill 目录下的 `assets/fishbone-template.drawio`（只用这一份，不要在磁盘上搜索别的模板）。
> 所有命令都在**实验仓库根目录**运行。

## 不可违反的主持规则

1. **一次一问**：每轮只问一个问题，等回答后再决定怎么追问。这是对话，不是问卷。
2. **业务语言**：不说“认知维度”“质量维度”这类框架词，除非对方主动问框架。
3. **逐条确认**：每条障碍改写成便签后，读给对方确认才能入图。一个回答里拆出两条时，可以编号一起读，请他们逐条说对不对。
4. **主动探测，但不发明障碍**：对方没提到的方面也要主动问；但对方确认“这方面没问题”，就记为空，不能用行业经验或角色卡里的事例替他们填。
   你读过角色卡，但**不要先把卡里的事例说出来**引导对方，只用他们的业务用语（评审会、拒绝话术、需求反馈……）来问。
5. **不推荐方案**：不谈 AWS 服务、模型、RAG、数据库、提示词怎么写。方案会改变对方描述问题的方式。
6. **方案 → 障碍**：对方提了方案（“加个人工审核就行”“接个知识库”），反问“如果没有这个办法，最容易出什么具体错误？”，把方案放进 parking lot，把底层风险记为障碍。
7. **兜底 ≠ 没障碍**：对方说“我们有人工兜底 / 会上会过一遍”时，用中性的事实问题追问：“最近一次兜底兜住的是什么情况？有没有它兜不住的？”。只有对方确认存在问题，才提炼成障碍。
8. **保留原意**：保留原话里的数字、系统名和例子。“60 条要两个工作日”比“效率低”有用得多。
9. **“不知道 / 没有”是有效回答**：接受，不追着要数字；追问一次仍说不清的，记为 `unresolved`，不入图。
10. **脱敏**：不记人名、账号、手机号、邮箱、真实客户名（自己的场景尤其注意）；qa-record 只记脱敏后的摘要，必要处写 `[REDACTED]`。
11. **不覆盖**：输出目录已存在就换个名字（例如加 `-2`），workshop 产物是可审计记录。
12. **不手拼 XML**：drawio 只由 `scripts/generate_fishbone.py` 生成。

## 模式与时间

| 模式 | 用时 | 每个方面 | 顺序 |
|------|------|----------|------|
| **express 快速版（默认）** | 约 15 分钟，约 16–22 轮问答 | 开门问 + 最多 1 次追问；最多 2 张便签 | 责任 → 质量 → 认知 → 成本 → 性能 → 其他（红线先问） |
| standard 标准版 | 30–40 分钟 | 至少 2 个探测方向；最多 3 张便签 | 认知 → 质量 → 责任 → 成本 → 性能 → 其他 |

快速版的节奏：开场 1 轮，场景确认 1 轮，每个方面 2–3 轮（问 → 确认便签 → 需要时追问一次），最后整体确认 1 轮。某个方面已经得到 2 条清楚的障碍就转到下一个方面。

## 流程

### 第 0 步：准备（不问问题之前先做完）

```bash
test -f data/scenario/role-card.md && test -f .claude/skills/adlc-fishbone/assets/fishbone-template.drawio && echo ok
python3 .claude/skills/adlc-fishbone/scripts/generate_fishbone.py --check-template
TZ=Asia/Shanghai date +%F
```

- 第一条不是 `ok`：不在实验仓库根目录，先 `cd` 过去。模板校验 `success` 不是 `true`：停下来报告（模板被改过），不要猜格子位置。
- 读一遍 `data/scenario/role-card.md`（实验场景要用它拟场景定义；访谈中不要引用卡里的事例）。
- 发开场白，只问一个问题（组名）：

> 接下来我们先不讨论用什么技术实现，只确认这个 Agent 服务谁、要完成什么任务，以及什么问题会阻止它稳定上线。我每次只问一个问题，会把你们的原话整理成便签，你们确认后才放进图里。
> 先问一下：你们是第几组？（默认用快速版和实验场景——你们扮演角色卡里的需求评审小组；想用自己组的 Agent 场景，或想用 30–40 分钟的标准版，直接说。）

### 第 1 步：场景定义（1–3 轮）

**实验场景（默认）**：按角色卡第 1 节拟一句话定义，读给他们确认（一个问题）：

> 我理解的场景是：“给产品经理和客户成功经理用的需求反馈分诊 Agent：每条需求反馈判断是否重要、是否紧急、迭代 / 拒绝 / 待评估，拒绝时写内部理由和可以直接发给客户的话术。”这样描述准确吗？

图表头四项：`customer` = “示例 CRM PaaS 产品部（<组名>扮演）”，`use_case` = “需求反馈分诊 Agent”，`service_target` = “对内（产品经理、客户成功经理）”，`date` = 今天。

**自己的场景（可选）**：依次问（一次一个；快速版只问 ①②⑤，不清楚时再问 ③④）：
① 这个 Agent 主要给谁用？② 如果只能做好一件事，最重要的是什么？③ 回答或行动前要从哪些系统、文档、数据取事实？④ 它只回答，还是还会查询、创建、修改、审批或通知？⑤ 哪种错误一旦发生，你们会立刻叫停上线？
然后拟一句话定义请他们确认。告诉他们：下一步的判据环节里，实验自带的评估器多半覆盖不了他们的判据，补黄金样本也只适用于实验场景。

**确认后**建输出目录（`outputs/` 已在 .gitignore 里）：

```bash
mkdir -p outputs/fishbone && mkdir outputs/fishbone/<组名>-<YYYY-MM-DD>   # 组名只用字母、数字、汉字和 -，例如 第3组 → 第3组
```

`mkdir` 报“已存在”：问一个新名字（建议加 `-2`），**不要覆盖**。

### 第 2 步：五维障碍发现

每个方面的节奏：**开门问 → 听 → 追问一个方向（用他们的话）→ 改写成便签 → 读回确认 → 转到下一个方面**。
下表的“追问方向”不是要照念的问题，是根据对方刚说的话选方向、自己组织措辞。

便签：一条一个障碍；写事实不写方案；保留关键数字和系统名；40–50 字以内（过长就拆成两条，不删关键条件）。确认句式：
“我准备把它记为：‘<便签>’。这个说法准确吗？”——对方修正就按修正重写，不保留被否定的版本。

**责任 —— 出了事谁负责？**（快速版第一个问；可以接着场景问题⑤）
开门问：它绝对不能看到、说出或执行什么？什么情况下必须停下来交给人？

| 信号 | 追问方向 |
|------|----------|
| 隐私、敏感数据、个人信息 | 哪些数据只能特定角色看到？会出现在哪些输出里？ |
| 审批、不能自动 | 哪些结论必须人来拍板？边界不清时默认做还是默认不做？ |
| 出了问题、兜底、人工介入 | 什么情况必须升级给人？兜底兜不住的是哪类？ |
| 合同、合规、对外承诺 | 输出要符合哪些合规要求？哪些话一旦说出去收不回来？ |
| 追责、审计 | 出问题后能不能还原它依据什么做的判断？ |

**质量 —— 靠不靠谱？**
开门问：它给出什么样的结果，会让用的人马上不再信任它？

| 信号 | 追问方向 |
|------|----------|
| 每次不一样、前后矛盾 | 同一条输入跑几次，最怕哪种不一致？ |
| 漏掉、没检查到 | 哪些检查项或诉求最容易被漏掉？ |
| 没法直接用 | 它的输出能直接用，还是要人再改一遍？ |
| 千篇一律、模板回复 | 有没有“不同问题收到同一套回答”的情况？ |
| 依据、出处 | 哪些结论必须说出依据？怎么验证它说的是对的？ |
| 被带偏、被施压 | 输入里有情绪、施压或夹带指令时，它会不会跟着跑？ |

**认知 —— 它懂不懂？**
开门问：这个 Agent 最容易搞错或不理解的是什么？能举一个真实的例子吗？

| 信号 | 追问方向 |
|------|----------|
| 规则多、情况多 | 规则有多少条？写在一个地方还是散在多处？ |
| 术语、说法不一样 | 哪些说法最容易被混淆？同一件事不同人怎么说？ |
| 要看情况 | 同一个问题在什么条件下答案会不同？它怎么知道是哪种情况？ |
| 经常变、版本更新 | 规则或资料变了以后，它多久要知道？谁负责更新？ |
| 我们自己也说不清 | 连内部人员都说不清的判断，它给出结论大家能接受吗？ |

**成本 —— 划不划算？**
开门问：如果使用量扩大十倍，哪部分成本最可能失控？

| 信号 | 追问方向 |
|------|----------|
| 调用次数、费用 | 完成一条典型任务能接受花多少？有没有上限？ |
| 转人工、兜底 | 它处理不了转给人的量有多大？会不会反而增加人工？ |
| 反复、来回几次 | 同一件事要来回几次才能处理完？ |
| 维护、更新 | 它自己的资料和规则维护要多少持续投入？ |

**性能 —— 扛不扛得住？**
开门问：用的人最多愿意等多久？一次大概要处理多少？

| 信号 | 追问方向 |
|------|----------|
| 秒、实时、等不了 | 哪类任务必须几秒内完成，哪类可以等几分钟？ |
| 高峰、批量、排队 | 高峰时什么量级？排队了会等还是放弃？ |
| 超时、卡住 | 依赖的系统慢了或挂了，它应该怎么表现？ |
| 处理周期 | 有没有按小时或按天算完成周期的任务？时间窗多紧？ |

**其他 —— 还有什么会让它跑不下去？**（只放确实不属于五个方面的：系统集成、流程、组织、跨团队依赖）
开门问：除了 Agent 本身，还有什么系统、组织或流程问题会让它跑不下去？

通用追问技巧：**具体化**（能举个真实例子吗？）、**量化**（大概多少条 / 多少人 / 多久？）、**最坏情况**（真发生了最坏会怎样？）、**反转方案**（如果没有这个办法，最容易出什么错？）、**边界探测**（还有类似的情况吗？只追一轮）。

记空和记未确认：
- 追问一次后仍没有障碍：问“这个方面目前没有会挡住上线的问题，对吗？”，对方确认后记 `explored_empty`。
- 回答一直模糊（追问一次后仍说不清，或说“不知道”）：记 `unresolved`，把原话放进 qa-record，不入图。
- 每条障碍只归一个方面；跨方面的影响写进 `evidence`，不复制成多张便签。拿不准就归到最相关的那个方面，不轻易放“其他”。

每做完一个方面，把这一段的问答摘要追加到 `qa-record.md`（中途断了也有记录）。

### 第 3 步：取舍与最终确认（1–2 轮）

- 某个方面超过 3 条（快速版超过 2 条）：问“如果这个方面只能留 N 条，哪几条最可能阻止 Agent 上线？”。选中的 `selected: true`，其余留在 JSON 里当备选。
- 按方面把全部入图便签、记为空 / 未确认的方面和 parking lot **一次读回**，问：“可以按这个出图吗？”。
- 必须得到明确的“可以 / 确认 / 没问题”才设 `status: "approved_for_render"`；有修改就改完再读回确认。

### 第 4 步：保存数据

写 `outputs/fishbone/<目录>/fishbone-data.json`（以它为准）和 `qa-record.md`：

```json
{
  "schema_version": "1.0",
  "status": "approved_for_render",
  "metadata": {
    "customer": "示例 CRM PaaS 产品部（第3组扮演）",
    "date": "2026-11-20",
    "use_case": "需求反馈分诊 Agent",
    "service_target": "对内（产品经理、客户成功经理）",
    "participants": "第3组（4 人）",
    "mode": "express",
    "scenario": "lab"
  },
  "coverage": {"cognition": "confirmed", "quality": "confirmed", "responsibility": "confirmed",
               "cost": "confirmed", "performance": "unresolved", "other": "explored_empty"},
  "barriers": {
    "responsibility": [
      {"customer_quote": "脱敏后的原话", "sticky_text": "确认过的便签", "evidence": "例子或数字",
       "confirmed": true, "selected": true}
    ],
    "cognition": [], "quality": [], "cost": [], "performance": [], "other": []
  },
  "parking_lot": [{"original": "对方提出的方案", "converted_to": "responsibility[0]"}]
}
```

- `coverage` 只能是 `confirmed`（至少 1 条已确认障碍）、`explored_empty`（问过、对方确认为空）、`unresolved`（没问清楚）。
- `participants` 只写组名和人数，不写人名。`scenario` 为 `lab`（角色卡）或 `own`（自己的场景）。
- 先校验：`python3 .claude/skills/adlc-fishbone/scripts/generate_fishbone.py outputs/fishbone/<目录> --check-json`

`qa-record.md`（脱敏摘要，不是逐字聊天记录）：

```markdown
# 鱼骨图问答记录（已脱敏）
组：第3组 · 日期：2026-11-20 · 快速版 · 实验场景（角色卡）
一句话场景定义：……

## 责任
- 问：……
- 答（摘要）：……
- 便签（已确认，入图）：……
## 质量 / 认知 / 成本 / 性能 / 其他（同上；为空写“问过，确认为空”，没问清楚写“未确认：原话摘要”）
## Parking lot
- 方案：…… → 转成障碍：……
```

### 第 5 步：生成 drawio

```bash
python3 .claude/skills/adlc-fishbone/scripts/generate_fishbone.py outputs/fishbone/<目录>
```

退出码 0、`success: true` 才算完成；它写 `fishbone.drawio` 和 `validation-report.txt`（12 项检查各自的 PASS / FAIL）。
失败就按 `validation_errors` 改 JSON 后重跑，不要手改 drawio。便签过长会有 warning：拆短后重新确认。

### 第 6 步：预览（代替 PNG 导出）

实验 EC2 只能从 SSM 浏览器控制台进入，不能开端口、不能下载文件，所以把预览发到你们自己的私有 S3 桶，在笔记本浏览器的 S3 控制台里打开：

```bash
./tools/publish-define-pages.sh outputs/fishbone/<目录>
```

- 它会重新生成并校验 drawio，写出自包含的 `fishbone.html`，再连同 `fishbone.drawio` 上传到 `reports/define/<目录>/`，打印控制台链接。
- 网页：在已登录控制台的笔记本浏览器打开链接，点右上角「打开」。drawio：点「下载」，再用 app.diagrams.net 打开。
- 桶始终禁止公开访问；确认不了就什么都不上传并报错（报错时请联系讲师，不要自己改桶的设置）。只想在本地生成网页时加 `--no-upload`。

### 第 7 步：交付

告诉他们：输出目录、`qa-record.md`、`fishbone-data.json`（以它为准）、`fishbone.drawio`、`validation-report.txt`、预览链接；哪些方面记为空（`explored_empty`）、哪些没问清楚（`unresolved`）；parking lot 里有什么。
下一步：“接下来用 `adlc-criteria` skill 把这些障碍翻译成判据，看实验的评估器已经覆盖了哪些（约 10 分钟）。”
不要主动开始讨论方案或架构。

## 常见问题

- **对方说“有兜底，所以没问题”**：最常见的漏洞，用规则 7 追问。
- **对方给方案不给障碍**：用“如果没有这个办法，最容易出什么错？”反转，方案进 parking lot。
- **只问了一句就转了**：快速版每个方面开门问 + 1 次追问；标准版至少 2 个方向。
- **便签太长**：拆成两条，不删关键条件。
- **模板格子对不上**：`--check-template` 失败就停，模板更新后要重新核对 `generate_fishbone.py` 里的 Cell ID。
- **自己的场景含内部信息**：输出目录在 `outputs/`（不进 git）；预览页只在你们自己的私有桶里，不要把对象改成公开、不要外传链接。
