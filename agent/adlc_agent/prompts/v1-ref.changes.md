# V1 参考版相对 V0 改了什么

基于 v0；依据编写这份参考版时 V0 在实验自带的 30 条黄金集上的按需评估。你在第 4 章看到的是你自己的 V0 在 AgentCore Runtime 上、按你冻结的黄金集（例如 31 条）跑出的结果，条数和数字会不同，失败的类型通常相近。

编写参考版时，V0 的评估（按需评估和失败归因）发现：错得最多的是“处理建议”，维度上认知最多；V0 的工具只查得到功能名称，提示词也没有判断口径。V1 按下表逐条修改。模型、黄金集和能力目录数据都没有改。

| 失败原因（评估发现） | 修改（文件） | 预期影响的指标 |
|---|---|---|
| 认知：只查得到功能名称，分不清“已支持 / 部分支持 / 明确不做”，平台已支持的需求判成“待评估”或“迭代” | 工具 `tools.py`：`lookup_capability` 换成 `search_capabilities`，返回支持状态、说明、限制、替代方案和菜单路径 `how_to` | 处理建议准确率；“应拒绝”用例的整条答对率 |
| 认知：单个客户的定制被当成通用需求 | 工具 `tools.py`：新增 `find_similar_requests`，统计上个月有几个不同客户提过 | 是否重要准确率 |
| 质量、责任：“重要 / 紧急”被客户的措辞带偏（例如客户没说着急，就判不紧急） | 提示词 `prompts/v1-ref.md`：写明判断口径，≥3 个不同客户才算通用；“紧急”要有影响正在发生或 30 天内硬性节点的事实 | 是否重要、是否紧急准确率 |
| 责任：数据丢失、安全、合规、合同承诺、线上缺陷类需求不能被拒绝（误拒是红线） | 提示词：“不可自动拒绝”清单，这类只能判迭代或待评估；必须修复的缺陷判迭代 | 红线（误拒）保持 0 条；处理建议准确率 |
| 质量：拒绝话术空泛、没有替代方案 | 提示词：话术三段式（理解诉求 → 说明原因 → 替代方案），不承诺上线时间，不提其他客户 | 拒绝话术通过率；话术分项“替代方案” |
| 修 V1 红线（第一步）：早先的 V1 在话术里写菜单路径，话术评审拿到的能力目录摘录里没有菜单路径，核实不了，判为“编造配置路径”（红线，每次 7–9 条） | 提示词 + 工具：只说能力目录里写明的事实；话术里不写能力编号、相似需求的客户数和内部口径；“明确不做”的不说“暂时”；当时先不写菜单路径（工具也不返回 `how_to`） | 红线 0 条；拒绝话术通过率 |
| 评审加入菜单路径（第二步）：不写路径以后，评审常点评“缺少入口”，点评里提到“入口 / 路径”的每次 7–12 条，话术均分 0.80 | 评估器 + 工具 + 提示词：话术评审的能力目录摘录加入每项能力的菜单路径 `how_to`，评分标准写明路径怎么判（与所说功能在目录里的路径一致不算编造；改动任何一级、安到别的功能上、目录里没有的算红线）；V1 的工具重新返回 `how_to`，提示词要求只能原样照抄 | 话术红线保持 0 条；拒绝话术评审均分 |

## 两次后续修改的实测（编写参考版时：30 条自带黄金集，本地打分）

- 第一步之后：V1 连续 3 次运行都通过，红线 0 条（之前每次 7–9 条）。
- 第二步之后：早先那版 V1 的同一份输出用新评审重新打分，和菜单路径有关的红线从 8 条降到 2 条，剩下的 2 条正是目录里没有的路径。现在的 V1 本地全量运行 9 次都通过，红线都是 0 条；话术里的 116 条菜单路径全部是目录原文。评审点评里提到“入口 / 路径”的降到每次 2–5 条，话术评审均分 0.80 → 0.84，0.9 分以上的占比 12% → 36%。
- 评审改了以后，V0 和早先那版 V1 的输出都用同一个新评审重新打过分，所以 V0 → V1 的对比用的仍是同一套评估器；黄金集没有改。
