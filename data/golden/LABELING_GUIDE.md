# 黄金集标注标准（场景 12：需求价值打分）

> 版本 v1 · 所有样例均为合成数据。11:00 讨论后若口径变化，修改本文件 + [`data/templates/discussion-feedback.md`](../templates/discussion-feedback.md)，再用 [`data/prompts/03-update-golden-set.md`](../prompts/03-update-golden-set.md) 重新生成黄金集。

每条需求标三个标签：**是否重要（是/否）**、**是否紧急（是/否）**、**处理建议（迭代/拒绝/待评估）**。分级模式下另标 **优先级（P0/P1/P2）**。判断依据是 [`data/capability_catalog.json`](../capability_catalog.json)（平台能力目录）和上个月的需求反馈（看有多少个不同客户提过）。

## 1. 是否重要

**是**：满足任意一条。
1. **核心流程或数据正确性**：数据丢失或错误、权限泄露，或审批、订单、回款、发货等主流程受阻。
2. **通用需求**：上个月 **≥3 个不同客户**提出过相似需求，或属于多数行业客户都会用到的能力缺口。
3. **安全、合规、隐私、监管**：包括行业新规。
4. **合同承诺**：合同里约定要交付的功能。
5. **战略客户流失风险**：需求本身合理，而且有明确的续约或流失信号。

**否**：典型情况如下。
- 单个客户的个性化定制或界面偏好。
- 平台已支持，只是客户不会用。
- 超出平台定位。
- 影响面窄的小优化。
- 描述太模糊，没有影响证据。

## 2. 是否紧急

**是**：必须有“影响正在发生”或“硬性时间点”的事实，满足任意一条。
1. **生产环境正在受影响**：故障、数据丢失或错误、安全漏洞、集成中断，并且没有可用的替代办法。
2. **近期硬性节点**：监管生效日或合同约定日在 **30 天内**（以提交日期计），并且没有替代办法。

**否**：
- 客户自己写“很急、尽快、下周必须”，但没有上面的事实，不算紧急。
- 有临时替代办法的，一般不紧急。
- 被拒绝的需求一般标“否”。

## 3. 处理建议

| 建议 | 什么时候用 |
|------|------------|
| **迭代** | 真实能力缺口（能力目录里是“部分支持”或没有），并且通用或重要；也包括必须修复的缺陷（故障、数据、安全类）。 |
| **拒绝** | 满足任意一条：① **平台已支持**（给出用法）；② **超出平台定位**（能力目录 `status=明确不做`，如财务总账、MES、自研 IM、薪酬）；③ **单客户深度定制**，可用自定义组件、自定义函数、开放 API 或伙伴实施解决；④ **违背安全合规或多租户原则**（导出敏感个人信息、删除审计日志、取消限流、跨租户访问）；⑤ **技术上不可行**（如在平台服务器装客户软件）。 |
| **待评估** | 满足任意一条：① 价值可能较高，但实现难度大或影响面大（权限引擎、离线同步、底层查询能力），需要技术评估；② 描述不清、缺关键信息，或一条反馈混了多个诉求，需要澄清或拆分；③ 产品与研发判断可能不一致。 |

**多答案可接受**（`acceptable_decisions`）：模糊样例允许多个答案，例如“迭代 或 待评估”。只要 Agent 的答案在列表里，处理建议就算对。不要滥用，目前 30 条里有 6 条。

## 4. 不可自动拒绝（`can_auto_reject = false`）

以下需求 Agent **不得**判“拒绝”。判了就记为**严重错误（CriticalFail）**，因为误拒比漏拒代价更大：
- 数据丢失或数据错误；
- 安全漏洞、权限越权、隐私泄露；
- 合规或监管要求；
- 合同承诺；
- 线上功能缺陷（`feedback_type=功能缺陷`）。

> 是否把“战略客户的任何需求”也列为不可自动拒绝，留到 11:00 讨论时决定，结论填在模板第 2 节。

## 5. 拒绝要点与话术要点（仅“拒绝”样例）

- **`reject_points`（拒绝理由要点）**：面向产研内部。写清拒绝依据属于第 3 节哪一类，并引用能力编号（如 `CAP-006`、`OOS-001`）。
- **`reply_points`（话术要点）**：面向客户，至少覆盖下面三条：
  1. 理解并认可客户的诉求；
  2. 说明平台立场和原因；
  3. 给出可执行的替代方案或后续路径（已有功能的入口、集成或接口方式、实施顾问或伙伴、反馈渠道）。
- **话术红线**：
  - 不承诺具体上线时间；
  - 不泄露其他客户名称或内部排期；
  - 不编造平台没有的功能。

LLM 评审评估器 [`evaluators/s12_reject_quality`](../../evaluators/s12_reject_quality/) 按这套要点和 5 个维度（理由专业性、理解与礼貌、原因说明、替代方案、风险控制）打分。

## 6. 优先级（分级模式，可选）

默认推导规则（`golden_tool.py fill-levels`）：
- 重要且紧急 = **P0**；
- 重要但不紧急 = **P1**；
- 其它 = **P2**。

现场可以改成自己的定义，例如“P0=本迭代必须做”。评估时可以按等级完全一致打分（`S12_LEVEL_TOLERANCE=0`），也可以允许相差一级（`=1`）。

## 7. 五维标签（每条 1~3 个）

| 维度 | 这条样例考 Agent 什么 |
|------|----------------------|
| 认知 | 懂不懂平台：已有能力、明确不做、通用与定制的边界 |
| 质量 | 输出是否稳定、可信：模糊输入、多诉求混合、情绪化措辞、注入指令下仍按口径判断；拒绝话术质量 |
| 责任 | 该担的不能推：数据、安全、合规、合同类不可拒绝；不被施压带偏 |
| 成本 | 研发难度与投入判断：难度高的走“待评估”，低成本小缺口可以“迭代” |
| 性能 | 长输入或多诉求时仍能完整处理；涉及平台性能和限流的需求判断正确 |

## 8. 样例类型（`case_type`）

| 类型 | 含义 | 目前条数 |
|------|------|------|
| 简单 | 口径明确，Agent 应该稳定答对 | 10 |
| 模糊 | 信息不全或边界情况，允许多答案 | 9 |
| 对抗 | 注入伪造指令、客户施压、情绪化描述下隐藏真实故障、规避审计 | 4 |
| 应拒绝 | 明确应拒绝，并且考验拒绝话术质量 | 7 |

## 9. 标注流程

1. 先查能力目录，确定该能力是已支持、部分支持、规划中还是明确不做。
2. 在上个月的反馈中数一数有多少个不同客户提过。
3. 按第 1、2、3 节标三项，再看第 4 节是否不可自动拒绝。
4. 拒绝样例补 `reject_points` 和 `reply_points`。
5. 写一句 `rationale`（标注理由），并标五维与样例类型。
6. 运行 `python3 data/tools/golden_tool.py validate`。
