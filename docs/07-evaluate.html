7.3

读懂分数：三项准确率 vs 70% 目标

5 分钟

看是否重要、是否紧急、处理建议三项各自的准确率是否达标。

看哪个数含义怎么判断
是否重要 / 是否紧急 / 处理建议（label_important / urgent / decision 的平均分）三项各自的准确率，直接对应场景目标三项都 ≥ 70% 才算达标
label_accuracy每条需求三项里对了几项（0、0.33、0.67、1）看整体；CriticalFail = 把不可拒绝的需求拒绝了，最严重
reject_quality / reject_quality_llm拒绝理由和话术的质量（只统计 Agent 判了“拒绝”的条目）≥ 0.7 为合格
Builtin.Correctness / Helpfulness内置评估器的通用视角作为参考，不作为目标
V0 本来就设计得偏弱，第一次不达标是正常的——这正是“评估驱动”的起点：有了分数，才知道改哪里、改完有没有用。
7.4

在控制台查看评估结果

5 分钟

在 CloudWatch / Evaluations 控制台看到同样的分数和解释，Demo 时直接用。

  1. CloudWatch → GenAI Observability → Bedrock AgentCore → 点你的 Agent（A 版 s12lab-zhang3-local-agent，B 版 s12lab_zhang3_agent）。
  2. Sessions / Traces：30 个新 session；点开任一 trace 看 Agent 的推理、工具调用和输出。
  3. Evaluations 页签：在线评估的结果。session 空闲 2 分钟后才开始打分，所以 7.1 跑完后约 5–10 分钟才会陆续出现；可以看到每个评估器的平均分、分布和每个 session / trace 的得分与解释。
  4. （可选）CloudWatch → Metrics → 命名空间 Bedrock-AgentCore/Evaluations，可以给评估分数配告警。
预期结果：Evaluations 页签里 label_important / label_urgent / label_decision 的平均分与 7.2 的三项准确率基本一致（在线评估不传黄金集参考输入，评估器用自带的黄金集按需求编号对答案）。
7.5

找出失败用例并按五维归因

5 分钟

列出判错的需求，按五维（认知 / 质量 / 责任 / 成本 / 性能）归因，第 8 章就改这些。

python3 - <<'EOF'
import json, glob, os
f = max(glob.glob('results/eval-*.json'), key=os.path.getmtime)
d = json.load(open(f, encoding='utf-8'))
print('评估结果文件：', f)
for s in d['sessions']:
    sc = s['scores'].get('label_accuracy', {})
    if sc.get('label') != 'Pass':
        print(s['feedback_id'], sc.get('label'), (sc.get('explanation') or s.get('error') or '')[:160])
EOF
预期输出（示意）：

FB-2610-003 CriticalFail ...
...

对照黄金集里每条的 dimensions（五维标签）和 rationale（标注理由），把错误归类：

维度典型失败现象多半是哪里的问题
认知平台已支持的能力被判“迭代”；超出定位的需求没被拒绝；单客户定制被当成通用需求工具拿不到能力状态 / 没查相似需求（V0 的工具缺陷）
质量拒绝理由空泛、话术没有替代方案；“重要”判断标准不一致提示词缺少判断口径和话术要求
责任数据丢失、安全、合规、合同承诺类被拒绝（CriticalFail）；被“下周必须上线”带偏判紧急提示词缺少“不可自动拒绝”规则和紧急的事实标准
成本价值高但难度大的需求被直接承诺“迭代”，没有“待评估”缺少难度 / 影响面的判断口径
性能超时、单条耗时过长、token 过多模型选择、工具返回内容过长
