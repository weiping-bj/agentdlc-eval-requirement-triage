8基于评估优化（V0 → V1） A/B 通用

根据失败用例改进 Agent：提示词、工具、数据或模型。我们准备了参考答案 V1，你也可以让 coding agent 自己改出一个 V2。

8.1

常见优化方法一览

3 分钟

知道问题出在哪类，该改哪里：提示词、工具、能力目录还是模型。

失败现象（来自 7.5）五维改哪里V1 里的做法
分不清“已支持 / 真实缺口 / 明确不做”认知工具输出：tools.pysearch_capabilities 返回状态、限制、替代方案
单客户定制当成通用需求认知新增工具find_similar_requests 统计上个月有几个不同客户提过
“重要 / 紧急”标准不一致，被客户措辞带偏质量 责任提示词口径：prompts/v1.md写明判断条款：≥3 个客户才算通用；“紧急”必须有影响正在发生或 30 天内硬性节点的事实
数据丢失 / 安全 / 合规 / 合同承诺类被拒绝责任提示词红线“不能自动拒绝”清单，遇到必须判迭代或待评估
话术空泛、没有替代方案质量提示词输出要求话术三段式：理解诉求 → 说明原因 → 替代方案 / 后续路径；不承诺上线时间
能力目录本身缺条目、写错状态认知数据：capability_catalog.json（V1 未改数据；现场发现目录不准时改这里，B 版需重新部署）
太慢、太贵、偶发超时成本 性能模型：config/lab.env 的 AGENT_MODEL_ID可用 ./tools/use-model.sh <模型ID> 试更快的模型，再用同一黄金集评估比较
自有 Agent 怎么对应（A 版接入你们自己的 Agent）
上表“改哪里”一列换成你们 Agent 里对应的地方：
  • 提示词（prompts/v1.md 的判断口径、红线、话术要求）→ 你们 Agent 的系统提示词。
  • 工具输出 / 新增工具（tools.py）→ 你们 Agent 的工具或函数：能力查询要返回哪些字段（支持状态、限制、替代方案），要不要加一个“查相似需求”的工具。
  • 数据（capability_catalog.json）→ 你们的知识库或能力数据源。
  • 模型（AGENT_MODEL_ID）→ 你们 Agent 的模型配置。
同样不要改黄金集和评估器，只改你们的 Agent。

改之前先做一次基线（优化前）：用原来的 Agent 处理同样的 30 条黄金集，按 A4.2 的格式导出日志（每条带 feedback_id），然后 ./11-A-convert-logs.sh check / send → ./12-A-check-telemetry.sh → ./31-run-eval.sh，记下 send 输出里的 run_id（A-imported-<时间>）。8.2 分析它，第 9 章用它当“优化前”。

优化 Agent 时不要改黄金集和评估器——否则前后分数不可比。黄金集只在第 2 章按业务口径修改。
8.2

用 coding agent 分析失败用例并提出修改

10 分钟

把评估报告交给 coding agent，让它给出具体修改建议并写出新版本提示词（V2）。

这段提示词让 coding agent 自己读 results/eval-*.json 和黄金集，所以只需要 7.2 的评估结果；7.5 的输出不是它的输入。时间紧的组可以 7.2 做完直接到这里。

在 EC2 上运行 claude（或你习惯的 coding agent），把下面整段提示词粘贴进去：

你在仓库 ~/scenario12-lab 中工作。目标：根据最新一次评估结果，改进“需求价值评审 Agent”的系统提示词，让“是否重要 / 是否紧急 / 处理建议”三项准确率都达到 70% 以上，并提高拒绝话术质量。

请按顺序完成：
1. 读取 results/ 下最新的 eval-*.json，列出 label_accuracy 不是 Pass 的用例（feedback_id、期望 vs 实际、explanation），以及 reject_quality 低于 0.7 的用例。
2. 对每个失败用例，到 data/golden/golden_set.jsonl 里找同一 feedback_id 的 rationale（标注理由）和 dimensions（五维），归纳出 3-5 条主要失败原因。
3. 阅读 agent/s12agent/prompts/v0.md、agent/s12agent/prompts/v1.md、agent/s12agent/tools.py 和 data/golden/LABELING_GUIDE.md（标注口径以它为准）。
4. 在 agent/s12agent/prompts/v1.md 的基础上写出 agent/s12agent/prompts/v2.md，针对第 2 步的原因修改判断口径、红线和话术要求；保持输出 JSON 格式完全不变（字段：feedback_id, important, urgent, decision, level, reasoning, reject_reason, customer_reply）。
5. 在 agent/s12agent/tools.py 的 TOOLSETS 里增加 "v2"，使用和 "v1" 相同的工具列表。
6. 不要修改 data/golden/、evaluators/、labkit/ 下的任何文件，也不要修改 v0.md / v1.md。
7. 最后用中文总结：改了什么、对应哪个失败原因、预计影响哪一项指标。
预期结果：coding agent 列出失败原因，生成 agent/s12agent/prompts/v2.md，并在 tools.py 里加上 "v2"。之后用 ./40-switch-version.sh v2 切换，按 8.4 / 第 9 章评估它。
自有 Agent：提示词要改的地方
  • 第 1 步：“results/ 下最新的 eval-*.json”换成你们基线那次的 results/eval-A-imported-<时间>.json（见 8.1）。
  • 第 3 步：三个 agent/s12agent/… 路径换成你们 Agent 的系统提示词文件和工具代码路径（先征得同意再把代码放到 EC2 上，只放需要的文件，第 10 章清理时删除）。
  • 第 4 步：改成“在你们现有的系统提示词基础上写出新版本，另存为新文件”；输出 JSON 字段那句保留（评估器按这些字段打分，见 evaluators/README.md 第 1 节）。
  • 第 5 步：删掉（TOOLSETS 只属于 mock agent）。
  • 第 6 步：“也不要修改 v0.md / v1.md”改成“不要修改原来的系统提示词文件”。
第 2、7 步不变。
时间紧时直接用我们准备好的 V1（8.3）。有余力的组可以 V1、V2 都评估，看看谁的分数更高。
8.3

切换到 V1（参考优化版本）

1 分钟

一条命令把 Agent 切换到我们准备好的优化版本。

先看看 V1 比 V0 改了什么：

git diff --no-index agent/s12agent/prompts/v0.md agent/s12agent/prompts/v1.md | head -60

文件：prompts/v0.md · prompts/v1.md · 工具差异见 tools.py 的 TOOLSETS。然后切换：

./40-switch-version.sh v1
预期输出： 
✅ Agent 版本已切换为 v1
   A 版：./10-A-run-local.sh golden      B 版：./20-B-deploy-runtime.sh 然后 ./21-B-run-golden.sh

脚本：40-switch-version.sh（写入 config/local.env 的 AGENT_VERSION）

自有 Agent
40-switch-version.sh 只切换本仓库 mock agent 的版本。你们的 Agent 按平时的方式把改好的版本发布到测试 / 预发环境（不要直接上生产）；第 9 章靠导入时的 run_id 区分前后两次。
用自己的 V2（8.2 生成的 prompts/v2.md）： 
./40-switch-version.sh v2
./00-config.sh | grep AGENT_VERSION
40-switch-version.sh 会先检查 agent/s12agent/prompts/v2.md 是否存在（用法提示里只写了 v0|v1，v2、v3 也可以）；第二条应显示 v2。tools.py 的 TOOLSETS 里没有 "v2" 时，V2 自动沿用 V1 的工具。之后按 8.4 让它生效、按第 9 章评估，要看的地方：
  • A 版 ./10-A-run-local.sh golden：“▶ 运行 30 条需求 · 路线 A · 版本 v2 …”这一行（在日志组、OTel 和 OpenTelemetry WARNING 几行之后）。
  • B 版 ./20-B-deploy-runtime.sh：第一行“▶ 部署 … · Agent 版本 v2 …”；然后 ./21-B-run-golden.sh 的“▶ 运行 … 版本 v2 …”。
  • 对比：./32-compare.sh 默认对比 V0 和最后评估的那个版本；要看 V1 → V2：./32-compare.sh --before <V1 的 run_id> --after <V2 的 run_id>（见 9.2）。
8.4

让 V1 生效：A 版重新本地运行 / B 版重新部署 Runtime

5 分钟

A 版在本地跑 V1，B 版把 V1 更新到 Runtime。

A 版
不需要部署：下一次 ./10-A-run-local.sh golden 会自动使用 V1（第 9 章）。确认当前版本： 
./00-config.sh | grep AGENT_VERSION
AGENT_VERSION               v1
B 版
重新部署（更新同一个 Runtime，生成新版本号；依赖包会复用，比第一次快）：
