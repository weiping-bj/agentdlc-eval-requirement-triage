A3.2

2 分钟

装上负责采集和发送 trace 的组件。

实验环境里安装脚本已经装好了（见 agent/requirements.txt），确认一下即可：

pip show aws-opentelemetry-distro strands-agents | grep -E '^(Name|Version)'
预期输出： 
Name: aws-opentelemetry-distro
Version: 0.x.x
Name: strands-agents

给你们自己的 Agent 安装：pip install "aws-opentelemetry-distro>=0.18" boto3；如果是 Strands Agent，再加 "strands-agents[otel]"。LangGraph / LangChain 等框架的支持情况见 AgentCore 文档 Telemetry setup and delivery。
A3.3

配置 OTel 环境变量（发往 CloudWatch）

3 分钟

告诉 ADOT 把数据发到哪个区域、哪个日志组、服务叫什么名字。

环境变量都写在 telemetry/otel_env.sh，执行一次看看效果：

source ./00-config.sh && source telemetry/otel_env.sh
预期输出： 
📡 OTel 已配置：service.name=s12lab-zhang3-local-agent · 日志组 /aws/bedrock-agentcore/s12lab-zhang3-local-agent · 区域 us-west-2
环境变量作用（一句话）
AGENT_OBSERVABILITY_ENABLED=true打开 ADOT 的 GenAI 观测默认设置：100% 采样，并把 session.id 写到每个 span 上
OTEL_PYTHON_DISTRO=aws_distro
OTEL_PYTHON_CONFIGURATOR=aws_configurator		使用 AWS 发行版的采集与发送配置（SigV4 签名，走实例角色）
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf发送协议
OTEL_TRACES_EXPORTER=otlpspan 发送到 X-Ray OTLP 端点，进入 CloudWatch 的 aws/spans
OTEL_LOGS_EXPORTER=otlp模型输入 / 输出内容作为日志事件发送
OTEL_RESOURCE_ATTRIBUTESservice.name = 控制台里显示的 Agent 名；aws.log.group.names = 关联的日志组
OTEL_EXPORTER_OTLP_LOGS_HEADERS模型输入 / 输出事件写到哪个日志组、哪个日志流
接入自己的 Agent 时，只要换服务名和日志组：source telemetry/otel_env.sh my-agent /aws/bedrock-agentcore/my-agent。日志组需要先存在（我们的脚本会自动创建：labkit/loggroup.py）。
A3.4

给每次请求带上 session.id（自有 Agent 需要改几行代码）

5 分钟

评估服务按 session 找数据，没有 session.id 就找不到。

在你们 Agent 处理一次请求的入口处，加 4 行代码（把同一条需求的所有 span 归到同一个 session）：

from opentelemetry import baggage, context

token = context.attach(baggage.set_baggage("session.id", session_id))  # 每条需求一个唯一 ID
try:
    result = agent(prompt)            # 你原来的 Agent 调用
finally:
    context.detach(token)

然后用 opentelemetry-instrument 启动你的程序（代码其它地方不用改）：

opentelemetry-instrument python your_agent.py

mock agent 的做法可以直接参考：

  • labkit/batch.py 的 _local_one()：设置 baggage session.id；
  • agent/s12agent/core.py 的 triage()：外层 s12lab.triage span，写入 s12lab.feedback_id、s12lab.agent_version 和最终结果 s12lab.triage_output（评估器优先从这里读 Agent 输出）。
评估器需要的数据：① 每个 span 带 session.id；② 一条需求 = 一个 trace；③ 能拿到 Agent 的最终输出（JSON）。Strands 框架自动产生 invoke_agent / chat / execute_tool span；其它框架看 A5 的检查结果决定要不要补。

A3.6

在 CloudWatch GenAI Observability 中查看 trace

3 分钟

在控制台确认数据已经到达。

  1. 打开 CloudWatch 控制台（右上角区域与实验一致）→ 左侧 GenAI Observability → Bedrock AgentCore。
  2. 在 Agents 列表里找到 s12lab-zhang3-local-agent（不在 Runtime 上的 Agent 也会列出，按 service.name 显示）。
  3. 点进去 → Sessions：能看到 3 个 session（名字形如 s12lab-zhang3-v0-FB-2610-001-…）→ 点任一 session → Traces：能看到 s12lab.triage → invoke_agent → chat / execute_tool lookup_capability 的调用树。
  4. （可选）CloudWatch → Application Signals → Transaction search：筛选 service.name = s12lab-zhang3-local-agent，看到原始 span。
预期结果：3 个 session，每个 1 个 trace；trace 里有模型调用和工具调用。

下一步：只有 Agent 埋点的组 → 直接到 A5 遥测检查；手里只有历史日志的组 → 先做 A4。
