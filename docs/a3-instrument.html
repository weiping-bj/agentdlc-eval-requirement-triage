A3埋点：OTel + ADOT → CloudWatch A 版

A 版把 mock agent 直接运行在实验 EC2 上，模拟一个不在 AgentCore Runtime 上的 Agent（例如运行在本地机房或其他云上）：这样的 Agent 要自己用 ADOT（AWS Distro for OpenTelemetry）埋点，把 trace 发到 CloudWatch。本章用 mock agent 走一遍这个过程，并讲解关键代码。

本章的命令都在实验 EC2 上执行。前提：已完成 1.8 开启 Transaction Search。现场不接入你们自己的 Agent；会后要接入，按 《自带 Agent 接入指南》 操作。
A3.1

先不带遥测跑一次 Agent

3 分钟

确认 Agent 本身能正常工作，排除和埋点无关的问题。

./10-A-run-local.sh smoke

脚本：10-A-run-local.sh → labkit/batch.py（逐条调用 Agent，结果写到 results/）

预期输出： 
▶ 运行 1 条需求 · 路线 A · 版本 v0 · 模型 us.anthropic.claude-sonnet-5-5 · 并发 1
  [ 1/1] FB-2610-001       11.9s  重要=是 紧急=否 建议=迭代
✅ 完成：1 条，用时 12s，失败 0 条 → results/run-A-smoke-215617.jsonl
   run_id = A-smoke-215617

每条需求大约 10–20 秒（Claude Sonnet 5.5），run_id 里的数字是当时的时间。

想看 Agent 的完整输出：tail -1 results/run-A-smoke-*.jsonl | python3 -m json.tool

pip show aws-opentelemetry-distro strands-agents | grep -E '^(Name|Version)'

Name: aws-opentelemetry-distro

A3.3

配置 OTel 环境变量（发往 CloudWatch）

3 分钟

告诉 ADOT 把数据发到哪个区域、哪个日志组、服务叫什么名字。

环境变量都写在 telemetry/otel_env.sh，执行一次看看效果：

source ./00-config.sh && source telemetry/otel_env.sh
预期输出： 
📡 OTel 已配置：service.name=s12lab-zhang3-local-agent · 日志组 /aws/bedrock-agentcore/s12lab-zhang3-local-agent · 区域 us-west-2
环境变量作用（一句话）
AGENT_OBSERVABILITY_ENABLED=true打开 ADOT 的 GenAI 观测默认设置：100% 采样，并把 session.id 写到每个 span 上
OTEL_PYTHON_DISTRO=aws_distro
OTEL_PYTHON_CONFIGURATOR=aws_configurator		使用 AWS 发行版的采集与发送配置（SigV4 签名，走实例角色）
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf发送协议
OTEL_TRACES_EXPORTER=otlpspan 发送到 X-Ray OTLP 端点，进入 CloudWatch 的 aws/spans
OTEL_LOGS_EXPORTER=otlp模型输入 / 输出内容作为日志事件发送
OTEL_RESOURCE_ATTRIBUTESservice.name = 控制台里显示的 Agent 名；aws.log.group.names = 关联的日志组
OTEL_EXPORTER_OTLP_LOGS_HEADERS模型输入 / 输出事件写到哪个日志组、哪个日志流
关键点：service.name 和日志组就是控制台里显示的 Agent 名，也是 6.5 在线评估筛选数据的条件（labkit/online.py 用 LOCAL_SERVICE_NAME / LOCAL_LOG_GROUP），所以这里用默认名，不要改。日志组要先存在：./10-A-run-local.sh trace / golden 会先创建它（labkit/loggroup.py）。自带 Agent 为什么也不要改名，见 指南 G.4。
A3.4

关键代码讲解：环境变量、session.id、最终输出

5 分钟

看 mock agent 怎样满足评估的要求：每个 span 带 session.id、一条需求一个 trace、能拿到最终输出。这一步只看不改，也不需要运行。

① 环境变量（A3.3）在启动前设置。10-A-run-local.sh 先建日志组、设置环境变量，再用 opentelemetry-instrument 启动批量脚本，ADOT 就在这个进程里工作：

"${_S12_PY}" -m labkit.loggroup "$LOCAL_LOG_GROUP"
source telemetry/otel_env.sh "$LOCAL_SERVICE_NAME" "$LOCAL_LOG_GROUP"
…
exec "$OTEL_BIN" "${_S12_PY}" -m labkit.batch --mode local --limit "$N" "$@"

② 每条需求一个新的 session.id，放进 OTel baggage。labkit/batch.py 的 _local_one()：

token = context.attach(baggage.set_baggage("session.id", sid))
try:
    return triage(items.item_of(row), version=version, model_id=model, session_id=sid)
finally:
    context.detach(token)

sid 形如 s12lab-zhang3-v0-FB-2610-001-<32 位十六进制>（_session_id()）。AGENT_OBSERVABILITY_ENABLED=true 让 ADOT 把 baggage 里的 session.id 写到之后产生的每个 span 上；评估服务按 session 取数据，一条需求 = 一个 session = 一个 trace。

③ 外层包一个 s12lab.triage span，把最终输出 JSON 写在上面。agent/s12agent/core.py 的 triage()：

with tracer.start_as_current_span("s12lab.triage") as span:
    span.set_attribute("session.id", session_id)
    span.set_attribute("s12lab.agent_version", version)
    if fid:
        span.set_attribute("s12lab.feedback_id", fid)
    …
    out = parse_output(text)
    …
    span.set_attribute("s12lab.triage_output", json.dumps(out, ensure_ascii=False))

这个 span 是每条需求的根 span，评估脚本靠它找到 trace；s12lab.triage_output 是评估器首选的读取位置（evaluators/README.md 第 2 节），不依赖 chat span 有没有记录消息正文；s12lab.feedback_id 用来和黄金集对应。

评估器需要的数据：① 每个 span 带 session.id；② 一条需求 = 一个 trace；③ 能拿到 Agent 的最终输出（JSON）。Strands 框架自动产生 invoke_agent / chat / execute_tool span，上面三段代码补上了其余部分。你们自己的 Agent 要加的同样三点（约 15 行，与框架无关），见 指南 G.5。

A3.6

在 CloudWatch GenAI Observability 中查看 trace

3 分钟

在控制台确认数据已经到达。

  1. 打开 CloudWatch 控制台（右上角区域与实验一致）→ 左侧 GenAI Observability → Bedrock AgentCore。
  2. 在 Agents 列表里找到 s12lab-zhang3-local-agent（不在 Runtime 上的 Agent 也会列出，按 service.name 显示）。
  3. 点进去 → Sessions：能看到 3 个 session（名字形如 s12lab-zhang3-v0-FB-2610-001-…）→ 点任一 session → Traces：能看到 s12lab.triage → invoke_agent → chat / execute_tool lookup_capability 的调用树。
  4. （可选）CloudWatch → Application Signals → Transaction search：筛选 service.name = s12lab-zhang3-local-agent，看到原始 span。
预期结果：3 个 session，每个 1 个 trace。实测的 trace 结构（span 名）：s12lab.triage → invoke_agent s12lab_triage_v0 → execute_event_loop_cycle → chat / execute_tool lookup_capability（另有一个 chat us.anthropic.claude-sonnet-5-5 是 Bedrock 调用本身）。模型的输入和输出内容在你的日志组 /aws/bedrock-agentcore/s12lab-zhang3-local-agent 里，晚 1–3 分钟出现。控制台菜单名称可能随版本略有不同。

下一步：A5 遥测检查。时间充裕时可以先做 A4（可选：用仓库自带的样例日志，演示“只有调用日志、没法改代码”时怎样导入并评估）。
