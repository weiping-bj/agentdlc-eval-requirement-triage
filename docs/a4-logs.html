A4已有日志：转换并导入 CloudWatch A 版

如果客户的 Agent 已经有自己的日志（但不是 OTel 格式），用转换脚本把日志变成 Evaluations 能读的 trace 并导入 CloudWatch。

适合“现场来不及改代码，但能导出最近的 Agent 调用记录”的组。仓库里带了一份样例日志，可以先用它把流程走通，再换成你们自己的日志。
A4.1

了解转换器需要哪些字段

3 分钟

评估至少需要：会话 ID、用户输入、模型输出、时间；有工具调用更好。

完整说明见 telemetry/LOG_FORMAT.md。格式是 JSONL：每次 Agent 调用一行。

字段必填说明
session_id是会话 ID；每条需求一个（评估按 session 取数据）
timestamp是调用时间，ISO 8601，例如 2026-10-15T09:30:00+08:00
user_input是发给 Agent 的内容（需求反馈原文）
agent_output是Agent 的最终输出；本场景最好是 0.5 节的 JSON（是否重要 / 是否紧急 / 处理建议…）
feedback_id建议需求编号，用来和黄金集对上；缺失时从 user_input 的“需求编号: …”里找
model · latency_ms · agent_name否模型名、耗时、Agent 名
tool_calls否工具调用列表：[{"name","input","output","status"}]
A4.2

把自有日志导出成 JSONL（按模板）

10 分钟

按模板把每次 Agent 调用整理成一行 JSON。

先看样例：telemetry/samples/customer-agent-logs.jsonl

head -1 telemetry/samples/customer-agent-logs.jsonl | python3 -m json.tool
预期输出（节选）： 
{
    "session_id": "cust-sess-0001",
    "timestamp": "2026-10-15T09:30:00+08:00",
    "feedback_id": "FB-2610-001",
    "user_input": "需求编号: FB-2610-001\n标题: 列表页批量修改自定义字段\n...",
    "agent_output": "{\"feedback_id\": \"FB-2610-001\", \"important\": \"是\", ...}",
    "model": "...",
    "latency_ms": 8200,
    "tool_calls": [ ... ]
}
你们的日志字段名不一样？把一两行原始日志和 LOG_FORMAT.md 一起交给 coding agent：“写一个脚本把这种日志转换成 LOG_FORMAT.md 的 JSONL 格式”。把转换后的文件放在仓库里，例如 mylogs.jsonl。
A4.3

先检查日志字段是否齐全

2 分钟

在导入前就发现缺字段的问题。

./11-A-convert-logs.sh check telemetry/samples/customer-agent-logs.jsonl

脚本：11-A-convert-logs.sh → telemetry/

预期输出：每个字段的覆盖率（例如 session_id 100%、tool_calls 0%），能否解析出三项标签，以及结论“可以导入 / 缺少必填字段”。
必填字段缺失（没有会话 ID、没有输出、没有时间）时不能导入。这种情况先和客户确认能否补导出；补不了就到 A5.3 切换到 B 版。
A4.4

转换并发送到 CloudWatch

5 分钟

把日志转换成 OTel trace，通过 ADOT 发到 CloudWatch。

./11-A-convert-logs.sh send telemetry/samples/customer-agent-logs.jsonl

脚本做了三件事：

  1. 把每行日志变成一组 OTel span（Agent 调用 + 工具调用 + 输入输出事件），格式和 Strands Agent 埋点产生的一致；
  2. 把时间平移到最近 14 天内（CloudWatch 不接收更早的 span），保留各条之间的先后间隔；
  3. 以服务名 s12lab-zhang3-imported-logs 发送到 CloudWatch，并登记为一次“运行”，后面 ./31-run-eval.sh 可以直接评估它。
预期输出：发送了多少个 session / span，以及 run_id = A-imported-…。
A4.5

在 CloudWatch 中确认导入结果

3 分钟

在控制台看到导入的会话和 trace。

  1. 等 2–3 分钟。CloudWatch → GenAI Observability → Bedrock AgentCore → Agents 列表找到 s12lab-zhang3-imported-logs。
  2. 点进去 → Sessions：session 名就是日志里的 session_id；点开看 trace 里的输入和输出。
预期结果：session 数量与日志行数（不同 session_id 的个数）一致。
