① 评估器清单：用了哪些评估器，各管什么

下表是这两次评估结果里出现的评估器。结论按三大支柱判：红线一条就不通过，门禁全部 ≥ 70% 才通过，观测只看趋势、不影响结论。

评估器类型衡量什么属于哪个支柱怎么用进结论
label_accuracy自定义 · 代码三项标签命中比例（0~1）；Pass = 三项全对，CriticalFail = 误拒了不可自动拒绝的需求（红线，整条记 0）红线观测误拒了不可自动拒绝的需求时返回 CriticalFail，算红线（误拒）；格式错误、整条通过率、五维准确率这些观测也从它读；分级模式下没有 label_level 时，优先级门禁也从它读
label_important自定义 · 代码“是否重要”单项对错（0/1），平均分即准确率门禁红线“是否重要”准确率门禁，≥ 70% 才达标；误拒的条目它也返回 CriticalFail，算红线
label_urgent自定义 · 代码“是否紧急”单项对错（0/1），平均分即准确率门禁红线“是否紧急”准确率门禁，≥ 70% 才达标；误拒的条目它也返回 CriticalFail，算红线
label_decision自定义 · 代码“处理建议”单项对错（0/1），平均分即准确率门禁红线“处理建议”准确率门禁，≥ 70% 才达标；误拒的条目它也返回 CriticalFail，算红线
reject_quality自定义 · Lambda 内 LLM 评审拒绝理由与客户话术质量（0~1，≥0.7 且无红线为 Pass；有红线 ≤0.2），只评“拒绝”条目红线门禁观测评审列出的红线（编造功能或配置路径、承诺上线时间等）算话术红线；评审分 ≥ 0.7 且无红线的拒绝占比是“拒绝话术通过率”门禁（≥ 70%）；五个分项和均分是观测
reject_quality_llm自定义 · LLM-as-judge同一套中文评分标准的原生 LLM 评审（5 档），只评“拒绝”条目观测同一套评分标准的原生评审（可挂在线评估），只看平均分，不进结论
Builtin.Correctness内置回答正确性（对照期望输出）观测只看平均分，不进结论
Builtin.Helpfulness内置回答有用性观测只看平均分，不进结论

误拒还有一个来源：Agent 判“拒绝”而黄金集标为不可自动拒绝（can_auto_reject = false），即使评估器没有标出，也算红线。评估器说明见 evaluators/README.md 和手册第 4 章。

提示词和工具按生成对比页时仓库里的文件对比；模型和评估器来自两次运行的记录。优化 Agent 时不改黄金集；评估器要改时，前后两个版本都要用改过的评估器重新打分，分数才可比。

V1 参考版相对 V0 改了什么

基于 v0；依据编写这份参考版时 V0 在实验自带的 30 条黄金集上的按需评估。你在第 4 章看到的是你自己的 V0 在 AgentCore Runtime 上、按你冻结的黄金集（例如 31 条）跑出的结果，条数和数字会不同，失败的类型通常相近。

编写参考版时，V0 的评估（按需评估和失败归因）发现：错得最多的是“处理建议”，维度上认知最多；V0 的工具只查得到功能名称，提示词也没有判断口径。V1 按下表逐条修改。模型、黄金集和能力目录数据都没有改。
