G自带 Agent 接入指南 会后自助

现场的 A 版和 B 版都用仓库自带的 mock agent。这份指南说明怎样把你们自己的 Agent 接到同一套评估流程（黄金集 + 评估器 + 对比页）：要么改几行代码、用 ADOT 埋点（路线一），要么只提供 Agent 的调用日志（路线二）。本页可以单独阅读。

标记说明（每一步标题右侧）：已实测 在真实账号里按本页步骤跑通过（2026-11-05 / 11-06，us-west-2）；按代码核对 对照仓库代码确认，没有单独实测；未验证 来自 AWS 文档或推断，请以你们的实际结果为准。
G.1

开始前：准备环境和数据

已实测

准备好运行脚本的机器、账号级设置和评估器，后面每一步都依赖它们。

  • 账号：一个专用的实验账号，不要用生产账号（脚本会创建 IAM 角色、Lambda、AgentCore 资源）。
  • 运行脚本的机器：按 第 1 章 建一台实验 EC2（推荐），或在自己电脑上 clone 仓库，在仓库根目录建虚拟环境并安装依赖：uv venv --python 3.12 .venv && uv pip install -r requirements.txt（见 requirements.txt 第一行），再在 config/local.env 里写 AWS_PROFILE（附录 X.1）。下面所有 ./…sh 命令都在仓库根目录执行。
  • 个人后缀：./tools/set-suffix.sh <后缀>。本页用 <后缀> 表示它（例如 zhang3），资源名都由它派生。
  • Transaction Search：./02-enable-observability.sh（1.8）。不开它，span 进不了 CloudWatch 的 aws/spans，评估服务就找不到数据。注意这是账号 + 区域级设置：它把这个区域所有 X-Ray trace 改为写入 CloudWatch Logs，并把 span 索引比例设为 100%，会产生 CloudWatch 费用；已经开着就不用再运行。要还原，只有本实验开启的情况下 ./99-cleanup.sh --all --account-level 才会还原（第 10 章）。
  • 黄金集和评估器：黄金集按 第 2 章 确认；评估器用 ./30-create-evaluators.sh 部署和注册（6.3）。

让你们的 Agent 处理哪些数据：黄金集的 30 条需求在 data/golden/golden_set.jsonl，每行的 input 字段就是 Agent 的输入（字段说明 feedback_item.schema.json），需求编号在 feedback_id。用同样的 30 条做“优化前”和“优化后”，分数才可比。

Agent 要输出什么：每条需求输出一个 JSON，字段见 evaluators/README.md 第 1 节：

{"feedback_id": "FB-2610-001", "important": "是", "urgent": "否", "decision": "迭代",
 "level": null, "reasoning": "…", "reject_reason": "", "customer_reply": ""}

important / urgent 取 是 / 否，decision 取 迭代 / 拒绝 / 待评估；判“拒绝”时 reject_reason 和 customer_reply 必填。标签准确率评估器按这些字段打分，解析不出时记 FormatError。

G.2

选择路线：改代码接入，还是只提供日志

两条路线最后都用同一组评估器、同一个对比页；区别在数据怎么进 CloudWatch。

路线一：改代码接入（ADOT 埋点）路线二：只提供日志
你们要做的事安装 ADOT、设置环境变量，在每次处理请求的入口加约 15 行代码把每次 Agent 调用导出成一行 JSON（JSONL 文件）
CloudWatch 里的数据Agent 运行时产生的真实 trace（含框架自己的 span、工具调用、token 用量）转换脚本按日志生成的 trace，时间重排到导入时刻
在线评估（控制台自动打分）支持，但服务名必须用实验默认名（G.4）不支持
按需评估 / 对比页支持，要先手动登记一次运行（G.8–G.9）支持，导入时自动登记
适合能改 Agent 代码，想上线后持续评估改不了代码，或想先快速看一次分数
步骤G.3–G.10（G.6 的在线评估可选）G.11–G.14

两条路线的优化与再评估都看 G.15，已知限制看 G.16。

G.4

路线一 ② 配置环境变量：用实验默认的服务名

已实测

告诉 ADOT 把数据发到哪个区域、哪个日志组、服务叫什么名字。

source ./00-config.sh && source telemetry/otel_env.sh
预期输出： 
📡 OTel 已配置：service.name=s12lab-<后缀>-local-agent · 日志组 /aws/bedrock-agentcore/s12lab-<后缀>-local-agent · 区域 us-west-2
环境变量（telemetry/otel_env.sh）作用
AGENT_OBSERVABILITY_ENABLED=trueADOT 的 GenAI 观测默认设置：100% 采样，并把 baggage 里的 session.id 写到每个 span 上
OTEL_PYTHON_DISTRO=aws_distro · OTEL_PYTHON_CONFIGURATOR=aws_configurator使用 AWS 发行版的采集与发送配置（SigV4 签名）
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf · OTEL_TRACES_EXPORTER=otlpspan 发到 X-Ray 的 OTLP 端点，进入 CloudWatch Logs 的 aws/spans（Transaction Search）
OTEL_LOGS_EXPORTER=otlp · OTEL_EXPORTER_OTLP_LOGS_HEADERS模型输入 / 输出内容作为日志事件，写到上面的日志组（日志流 runtime-logs）
OTEL_RESOURCE_ATTRIBUTESservice.name（控制台里的 Agent 名）和 aws.log.group.names（关联的日志组）
不要改服务名和日志组。在线评估（./33-online-eval.sh enable --path a）只看 LOCAL_SERVICE_NAME 和 LOCAL_LOG_GROUP 这两个值（labkit/online.py），它们由 labkit/config.py 的 derive() 按前缀和后缀算出来：在 config/local.env 或环境变量里设置它们不生效（会被覆盖）。如果给 otel_env.sh 传自己的名字（source telemetry/otel_env.sh my-agent …），trace 照样进 CloudWatch、按需评估也能用，但在线评估一条都不会打分。实测：同一个在线评估配置、同一段时间里，默认名的 session 3/3 被打分，自定义名的 0/5。

代价（如实说明）：控制台里你们的 Agent 显示为 s12lab-<后缀>-local-agent。如果用同一个后缀也跑过 mock agent（现场的 A3 / 第 7 章），两者的 session 会在同一个 Agent 名下。区分方法：mock agent 的 session.id 形如 s12lab-<后缀>-v0-FB-2610-001-<32 位十六进制>，G.5 的代码生成的形如 s12lab-<uuid>。想完全分开，可以用一个新后缀：在自己电脑上（没有实验权限边界）运行 ./tools/set-suffix.sh <新后缀> 后重新注册评估器（./30-create-evaluators.sh）；在实验 EC2 上后缀和 EC2 堆栈绑定（权限边界按后缀命名，换了后缀脚本会报“找不到实验权限边界”），要按 第 1 章 用新后缀重新创建 EC2 堆栈 按代码核对。

在你们自己的 shell 脚本里使用时，写成 source telemetry/otel_env.sh "$LOCAL_SERVICE_NAME" "$LOCAL_LOG_GROUP"（效果和不带参数一样）。不带参数 source 时，脚本自己的 $1 / $2 会被当成服务名和日志组（实测遇到过）。
Agent 不在这台机器上运行（容器、你们自己的服务器）：把上面这些环境变量按输出里的值设到运行 Agent 的地方，再设好 AWS_REGION 和能写 X-Ray、CloudWatch Logs 的 AWS 凭证。需要的 IAM 权限见 AgentCore 文档 “Add observability to agents hosted outside AgentCore Runtime” 未验证。
G.5

路线一 ③ 改代码：每条需求一个 session，最终输出写到 span 上

已实测

评估服务按 session 取数据，评估器要能读到 Agent 的最终输出；这段代码把两件事都做了。

把下面这段放在每次处理一条需求的入口（HTTP 接口的处理函数、队列的消费函数、批处理循环里的每一条），不要放在程序启动时。把 my_agent(item) 换成你们原来的 Agent 调用：它要返回一个 dict，字段见 G.1（返回的是 JSON 文本时先 json.loads）。

import json
import uuid

from opentelemetry import baggage, context, trace

tracer = trace.get_tracer("s12lab.triage")


def handle_one(item: dict) -> dict:
    """处理一条需求：一条需求 = 一个 session = 一个 trace。在每次处理请求的入口调用。"""
    session_id = f"s12lab-{uuid.uuid4()}"  # 每条需求一个新的唯一 ID
    token = context.attach(baggage.set_baggage("session.id", session_id))  # 之后产生的 span 都带上它
    try:
        with tracer.start_as_current_span("s12lab.triage") as span:
            span.set_attribute("session.id", session_id)
            fid = item.get("id") or item.get("feedback_id")  # 需求编号：按你们的字段名改
            if fid:
                span.set_attribute("s12lab.feedback_id", fid)
            result = my_agent(item)  # 换成你们原来的 Agent 调用；返回 dict，字段见 evaluators/README.md 第 1 节
            span.set_attribute("s12lab.triage_output", json.dumps(result, ensure_ascii=False, default=str))
            return result
    finally:
        context.detach(token)

同一段代码：telemetry/snippets/a34_session_wrapper.py（仓库里的测试会运行它，并检查我们的评估器能读出结果）。

这段代码做了什么为什么需要
每条需求生成新的 session.id，放进 OTel baggageADOT（AGENT_OBSERVABILITY_ENABLED）把它写到之后产生的每个 span 上；评估服务按 session 取数据，一条需求 = 一个 session = 一个 trace
包一个名为 s12lab.triage 的 span每条需求有一个可识别的根 span：按需评估、遥测检查和 G.9 的登记查询都靠它（或 invoke_agent span）找到 trace（labkit/spans.py）
写 s12lab.feedback_id 和 s12lab.triage_output需求编号用来对黄金集；最终输出 JSON 是评估器首选的读取位置（evaluators/README.md 第 2 节），不依赖框架有没有记录消息正文
  • 处理函数是 async 的（FastAPI 等）：把 def handle_one 改成 async def，把 my_agent(item) 改成 await my_agent(item)，其余不变。
  • 如果 Agent 把活交给自己开的线程或进程（线程池、multiprocessing 等），那里面的 span 可能拿不到这个上下文，session.id 会丢：尽量在同一个线程里调用 Agent，或者把 context 显式传过去 未验证。

实测方式：一个独立的 Strands Agent（不经过仓库的批量脚本）原样套用这段代码，跑 5 条黄金集需求；登记后 8 个评估器全部出分，A5 检查 🟩 通过（G.10）。

G.6

路线一 ④ 先建日志组，再开启在线评估（控制台自动打分）

已实测

日志组要先存在；在线评估要在 Agent 运行之前开启，开启之前产生的 session 不会被打分。

.venv/bin/python -m labkit.loggroup
./33-online-eval.sh enable --path a
预期输出： 
  🆕 创建日志组 /aws/bedrock-agentcore/s12lab-<后缀>-local-agent
…
✅ 已创建在线评估配置 s12lab_<后缀>_online_a（s12lab_<后缀>_online_a-…），采样 100%，session 空闲 2 分钟后打分
   之后每个新 session 都会自动评分，结果写入 CloudWatch：
   CloudWatch 控制台 → GenAI Observability → Bedrock AgentCore → 你的 Agent → Evaluations
日志组已经存在时显示 ✔ 日志组已存在 …；在线评估配置已经创建过时显示 ✅ 在线评估配置 … 已启用。不带参数时 labkit/loggroup.py 创建的就是 G.4 的默认日志组（保留 7 天）。
  • 为什么先建日志组：模型输入 / 输出事件要写进去；而且日志组不存在时 ./33-online-eval.sh enable --path a 会失败（见 G.16）。
  • 前提：评估器已注册（./30-create-evaluators.sh）。只想做按需评估（G.8–G.10）时可以不开在线评估，但日志组照样要建。
  • 先开启、再跑 Agent：只有开启之后产生的 session 会被打分；开启前的、以及改配置之前的旧 session 不会补打（实测）。
  • 在线评估没有“标准答案”输入：标签准确率评估器按需求编号到随 Lambda 打包的黄金集里找答案；不在黄金集里的需求返回 Skipped，不计分。
G.7

路线一 ⑤ 运行 Agent，到 CloudWatch 查看 trace 和分数

已实测

Agent 要在 opentelemetry-instrument 下启动，ADOT 才会工作；然后在控制台确认数据到了。

opentelemetry-instrument python your_agent.py
  • 在 G.4 的同一个 shell 里执行（环境变量要在）。用仓库的虚拟环境时写成 .venv/bin/opentelemetry-instrument .venv/bin/python your_agent.py。让它处理黄金集的 30 条（G.1），记下开始时间（G.9 要用）。
  • 数据怎么走：span → ADOT → X-Ray OTLP 端点 → CloudWatch Logs 的 aws/spans（Transaction Search）；模型输入 / 输出事件 → G.6 的日志组。进入 CloudWatch 有 1–3 分钟延迟。
  1. CloudWatch 控制台（区域与实验一致）→ GenAI Observability → Bedrock AgentCore → Agents：找到 s12lab-<后缀>-local-agent（不在 Runtime 上的 Agent 按 service.name 列出）。
  2. 点进去 → Sessions：每条需求一个 session（s12lab-<uuid>）→ Traces：根是 s12lab.triage，下面是框架自己的 span（Strands 是 invoke_agent → chat / execute_tool …）。
  3. Evaluations 页签：session 空闲 2 分钟后才开始打分，所以跑完约 5–10 分钟分数才陆续出现；也可以看 CloudWatch 指标命名空间 Bedrock-AgentCore/Evaluations（维度 service.name）。
  4. （可选）CloudWatch → Application Signals → Transaction search：筛选 service.name = s12lab-<后缀>-local-agent 看原始 span。控制台菜单名称可能随版本略有不同。
G.8

路线一 ⑥ 按需评估之前：先弄清“运行记录”

已实测

按需评估（./31-run-eval.sh）和遥测检查（./12-A-check-telemetry.sh）不扫描 CloudWatch，只评估登记过的运行。

一条“运行记录”由两部分组成：

  1. 运行文件 results/run-<run_id>.jsonl：每个 session 一行，把需求编号（feedback_id）和 session_id 对应起来。
  2. 登记项：.lab-state/runs.json（一个 JSON 数组）里的一个对象：run_id、运行文件路径、开始时间、日志组等。

仓库的脚本只登记自己产生的运行：mock agent 的批量运行（labkit/batch.py）和路线二的日志导入（labkit/convert_logs.py）。你们的 Agent 产生的 session 不会自动登记，要按 G.9 手动登记。

不带 --run 时评估的是最后一条登记的运行，不一定是你们的。./31-run-eval.sh 和 ./12-A-check-telemetry.sh 不带参数时取 runs.json 的最后一条（labkit/evaluate.py 的 pick_run()）。如果这台机器之前跑过 mock agent，它会悄悄评估那次 mock 运行，还可能显示 ✅ 达标，看起来像是你们的 Agent 达标了（实测）。从没登记过任何运行时，31 报 ❌ 还没有任何运行记录，12 报 ❌ 没有运行记录。所以：先登记，之后一律带 --run <run_id>，并核对输出第一行 ▶ 评估 run <run_id>：N 个 session 里的 run_id 和条数。

results/ 和 .lab-state/ 只在运行脚本的这台机器上（不提交到仓库），登记要在你运行 ./31-run-eval.sh 的同一台机器上做。

G.9

路线一 ⑦ 手动登记一次运行（4 步）

已实测

把你们这次运行的 session 写成运行文件并登记，之后 31 / 32 / 12 都能用它。

第 1 步：在 aws/spans 里找到这次运行的 session。CloudWatch → Logs Insights，日志组选 aws/spans，时间范围覆盖这次运行（例如开始前 5 分钟到结束后 5 分钟），运行：

fields @timestamp, attributes.session.id as sid, attributes.s12lab.feedback_id as fid,
       attributes.s12lab.triage_output as out, traceId
| filter name = "s12lab.triage" and resource.attributes.service.name = "s12lab-<后缀>-local-agent"
| sort @timestamp asc
| limit 1000

每行是一条需求：sid 是 session_id，fid 是需求编号，out 是最终输出 JSON。同一 session 只取一行。同一时间段也跑过 mock agent 时，去掉 sid 形如 s12lab-<后缀>-v0-… / -v1-… 的行（那是 mock agent 的）。记下第一行的时间（第 3 步要用）。@timestamp 可能按浏览器所在时区显示（例如北京时间比 UTC 早 8 小时），第 3 步要换算成 UTC。

第 2 步：写运行文件 results/run-<run_id>.jsonl（UTF-8，每个 session 一行）。run_id 只用字母、数字和 -，建议 A-own-<版本>-<开始时间>，例如 A-own-v0-20261106T113000Z：

{"run_id": "A-own-v0-20261106T113000Z", "version": "v0", "mode": "own", "feedback_id": "FB-2610-001", "session_id": "s12lab-0d3a2c0b-ca5f-456e-86b8-1745339607fd", "result": {"feedback_id": "FB-2610-001", "important": "是", "urgent": "否", "decision": "迭代", …}}
{"run_id": "A-own-v0-20261106T113000Z", "version": "v0", "mode": "own", "feedback_id": "FB-2610-002", "session_id": "s12lab-9be4edb8-…", "result": {…}}
字段必填用途（labkit/evaluate.py）
session_id是按它到 CloudWatch 查这个 session 的 span
feedback_id是黄金集里的需求编号：评估时据此把标准答案作为参考输入传给评估器
result建议Agent 的输出 JSON（第 1 步的 out 解析后的对象）；对比页的“实际”标签从这里取。没有就写 null
error否这条处理失败时写错误文字：评估时跳过这条
run_id · version · mode否只作说明；脚本用的是第 3 步登记项里的值

第 3 步：在 .lab-state/runs.json 末尾加一个登记项。先备份：cp .lab-state/runs.json .lab-state/runs.json.bak；文件不存在时新建，内容写成 [ {…} ]。

{"run_id": "A-own-v0-20261106T113000Z",
 "file": "results/run-A-own-v0-20261106T113000Z.jsonl",
 "created": "20261106T113000Z",
 "version": "v0",
 "mode": "own",
 "log_group": "/aws/bedrock-agentcore/s12lab-<后缀>-local-agent",
 "service_name": "s12lab-<后缀>-local-agent",
 "source": "aws/spans service.name=s12lab-<后缀>-local-agent",
 "count": 30, "model": "-", "agentRuntimeArn": null}
字段必填说明
run_id是和第 2 步一致；--run 用的就是它
file是第 2 步的运行文件，路径相对仓库根目录
created是UTC 时间，格式 YYYYMMDDTHHMMSSZ。写第 1 步第一行的时间（换算成 UTC）或更早：./31-run-eval.sh 从它往前 10 分钟开始查 span，./12-A-check-telemetry.sh 往前 60 分钟；写早了只是多查一段时间，写得比第一条请求晚 10 分钟以上就查不到（31 报 no spans found）。拿不准时区就再往前写 1 小时以上
version是v0（优化前）、v1（优化后）…：评估结果和对比页用它显示 V0 / V1
mode是写 own（对比页显示“自带 Agent（手动登记的运行）”）。不要用 local / runtime / imported，那是仓库脚本自己的运行类型

G.11

路线二 ① 日志需要哪些字段

已实测

转换脚本把每行日志变成一个 session / 一条 trace；缺必填字段的行不能导入。

格式是 JSONL（UTF-8）：每次 Agent 调用一行。完整说明：telemetry/LOG_FORMAT.md；样例：telemetry/samples/customer-agent-logs.jsonl。

字段必填说明
session_id是会话 ID，每条需求一个
timestamp是调用时间，ISO 8601（例如 2026-10-15T09:30:00+08:00）或毫秒时间戳
user_input是发给 Agent 的完整输入（需求反馈原文）
agent_output是Agent 的最终输出：最好就是 G.1 的 JSON（文本或对象都可以）；不是的话标签准确率评估器记 FormatError，只剩内置评估器可用
feedback_id建议黄金集里的需求编号；缺失时从输出 JSON 的 feedback_id 取
model · latency_ms · agent_name否模型名、耗时、Agent 名
tool_calls否[{"name","input","output","status"}]；没有时工具类评估器不可用
你们的日志字段名不一样：把一两行原始日志和 LOG_FORMAT.md 一起交给 coding agent，让它写一个转换成这种 JSONL 的脚本。给黄金集的 30 条各导出一行（每行带 feedback_id），才能和黄金集对上。日志里有真实客户数据时只放在运行脚本的机器上，建议放在 data/customer/（已在 .gitignore 里），不要提交到仓库。
G.12

路线二 ② 校验字段，再转换并导入 CloudWatch

已实测

导入前发现缺字段的问题；然后把日志转成 OTel trace 发到 CloudWatch，并自动登记成一次运行。

./11-A-convert-logs.sh check <你的日志.jsonl>
./11-A-convert-logs.sh send  <你的日志.jsonl>

脚本：11-A-convert-logs.sh → labkit/convert_logs.py。check 只读文件，不发送任何数据。

  • check：逐项列出字段覆盖率和“输出可解析为三项判断 JSON”的条数；出现 ✅ 字段检查通过 才继续；如果后面还有一行 ⚠️ 不到一半的输出能解析成三项判断，先调整 agent_output 的格式，否则标签准确率评估器会大量记 FormatError。有 ❌ 第 N 行缺少必填字段 / 不是合法 JSON / timestamp 无法解析 时先修正：缺必填字段或不是合法 JSON 的行，send 会直接跳过。
  • send：创建日志组 /aws/bedrock-agentcore/s12lab-<后缀>-imported-logs，以服务名 s12lab-<后缀>-imported-logs 发送；每行变成 invoke_agent <agent_name> → chat（+ 每个工具调用一个 execute_tool）的 trace；输出能解析成三项判断 JSON 时，写在根 span 的 s12lab.triage_output 上。
  • 时间按原先后顺序重排到最近几分钟内（每条间隔 10 秒），因为 CloudWatch 不接收 14 天以前的 span；也不会早于日志组的创建时间（CloudWatch Logs Insights 查不到比日志组更早的记录），所以第一次发送时记录从日志组建好后几秒开始排；行数多时后面的 session 会排到接下来的几分钟里，send 结尾会多一行 ℹ️ 提示要等多久（按代码核对，实测只跑了 5 行样例）；session_id 改写为 s12lab-<后缀>-imp-<发送时间>-<原 session_id>，同一文件重复发送也不会混在一起。
预期输出（send 的结尾，实测：样例日志 5 行）： 
✅ 已发送 5 个 session（run_id = A-imported-20261106T151120Z）。约 2-3 分钟后可在 CloudWatch 查到。
   下一步：./12-A-check-telemetry.sh   （检查数据能否被 Evaluations 使用）
记下这一行的 run_id（A-imported-<发送时间>），后面都用它。
