> **你在这里**：① 定义 → ② 构建 → ③ 评估 → **④ 发布** → **⑤ 观测** → ⑥ 回流 · 圆心：黄金标准

:image[你在这里：④ 发布 + ⑤ 观测]{src="/static/images/flywheel-release-observe.svg" width=220 height=220}

**用时**：约 10 分钟

发布环**用圆心做判定**：能不能发布，不靠感觉，按第 2 章签字的判据、第 4 章的三大支柱来判。观测环**复用圆心**：上线后用**同一组评估器**给真实流量打分，盯住质量有没有悄悄下滑。

## 6.1 发布结论：红线 0 条，门禁全部达标 {#s-6-1}

| 版本 | 红线 | 是否重要 | 是否紧急 | 处理建议 | 拒绝话术通过率 | 结论 |
|---|---|---|---|---|---|---|
| V0（第 4.5 步） | 1 条 | 68% | 81% | 39% | 50% | ❌ 不发布 |
| 我们自己的 V1（第 5.4 步） | 1 条 | 90% | 90% | 94% | 88% | ❌ 不发布：门禁全过，但红线一票否决 |
| V1 参考版（第 5.4 步） | 0 条 | 87% | 94% | 97% | 100% | ✅ 可以发布 |

*上表是一次实测；你的数字会有几个百分点的波动，按你自己的 5.4 结果填。*

判定规则只有一句：**红线 0 条，且每个门禁都达标，才发布**；有一条红线，准确率再高也不发布。观测指标（整条通过率、话术均分、`Builtin.*` 等）不进这个结论。

在本实验里，“发布”就是让 Runtime 的 **DEFAULT** 端点运行通过判定的那个版本。确认现在线上跑的是哪一版：

```bash
./30-deploy-runtime.sh status
```

**预期输出**（节选；`agentVersion` 就是线上的版本）：

```
{
  "agentRuntimeId": "adlc_ws_agent-VL2KJhC5Tp",
  "agentRuntimeVersion": "3",
  "agentVersion": "v1-ref",
  "modelId": "us.anthropic.claude-sonnet-5-5",
  "deployedAt": "2026-11-14T14:03:20.428419+00:00"
}
```

如果线上不是通过判定的版本，用第 5.3 步的两条命令切过去（`./50-switch-version.sh <版本>`，再 `./30-deploy-runtime.sh`）。只切到**跑过 5.4 并通过**的版本；V1 参考版还没评估过，就先跑完它的 5.4 再切。所有版本都不通过时，结论就是“不发布”（线上保持原样），6.2、6.3 照做。**回滚**也是同样两条命令，切回上一个通过判定的版本。

判据表里的指标读数（成本、性能、待评估占比）不在三大支柱的自动结论里，发布前还要人工对一眼，见 6.3。

发布记录（写在小组笔记里即可，本实验不提供发布记录工具）至少要能回答：发布的是哪个版本、用哪一版黄金集（`data/golden/MANIFEST.json` 的 sha256）和哪一组评估器（对比页 ③ 的评估器 ID）判定的、判定结果文件是哪个（`results/eval-<run_id>.json`）。

## 6.2 观测：在线评估里的分数 {#s-6-2}

第 4.3 步开启的在线评估，一直在给 Runtime 上的每个新 session 打分，门禁和红线评估器与发布前的按需评估**相同**（只少了两个只作观测的）。这里的“⑤ 观测环”说的是上线后的持续打分，和判据三档里的“观测档”（只看趋势、不进结论）不是一回事。

- **CloudWatch** → **GenAI Observability** → **Bedrock AgentCore** → `adlc_ws_agent` → **Evaluations** 页签。
- 右上角时间范围先选 V0 那次运行的时间段（从第 4.4 步开始前，到它跑完后 15 分钟左右：分数按打分时间归档，比 session 晚 10 分钟左右），记下 `label_important` / `label_urgent` / `label_decision` 的平均分；再选 V1 那次运行的时间段对比。时间范围同时包含两次运行时，看到的是混合平均，所以一定要分开看。
- 在 **Sessions** 里也可以按 session 名区分：V0 的 session 名含 `-v0-`，V1 参考版的含 `-v1-ref-`，你自己的 V1 含 `-v1-FB-`（`-v1-` 也会匹配到参考版）。
- （可选）**CloudWatch** → **Metrics** → 命名空间 `Bedrock-AgentCore/Evaluations`：各评估器的分数是指标，可以画成随时间变化的曲线，也可以配告警。

*图 6-2 分诊报告：这 60 条大部分不在黄金集里*

这 60 条里大部分不在黄金集中：在线评估仍会给话术质量和 Helpfulness 打分，标签评估器对不在黄金集里的条目返回 Skipped、不计分。这正是“上线后的持续评估”：没有标准答案的流量，也能盯住一部分质量；盯不住的部分（例如这些条目的标签对不对），就是下一轮回流要补进黄金集的。

再对照判据表里的指标读数看一眼：这次“待评估”19 / 60 = 32%，超过了业务方签字的“≤ 20%”；整批 60 条用了 140 秒，远低于 30 分钟。待评估占比这条不在本实验的自动结论里，但业务方把它签成了门禁：是接受这一版上线，还是下一轮继续压低待评估占比，由业务方决定，这也是下一轮回流的输入。成本（每条多少钱）本实验没有换算：token 用量在 trace 里，判据表里成本判据是“部分覆盖”。

## 检查一下：发布和观测有没有对齐黄金标准？ {#s-6-check}

**发布判定用的，和线上打分用的，是同一个圆心吗？** 发布前（5.4）和上线后（6.2）用的是同一版黄金集，门禁和红线评估器也相同；如果线上换了评估器或黄金集，在线分数和发布时的分数就不能放在一起比，“质量下滑”也就无从谈起。
