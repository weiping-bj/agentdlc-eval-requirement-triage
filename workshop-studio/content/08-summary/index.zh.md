## 8.1 你在每一环留下了什么 {#s-8-1}

AgentDLC 的每一环都应该留下一份**可以指认的产出物**；指不出来，这一环就等于没做。对一下你自己的实验目录：

| 环 | 和圆心的关系 | 你的产出物 | 在哪里 |
|---|---|---|---|
| ① 定义 | 产出圆心 | 鱼骨图、业务方签字的判据表、冻结的黄金集 | `outputs/fishbone/<目录>/`、`data/golden/MANIFEST.json` |
| ② 构建 | 遵循圆心 | 部署在 Runtime 上、trace 里带着结论的 Agent（V0 → V1） | `./30-deploy-runtime.sh status`；trace 里的 `adlc.triage` |
| ③ 评估 | 取用圆心 | 可复现的评估结果：固定的黄金集版本 + 固定的评估器 | `results/eval-*.json`、对比页 |
| ④ 发布 | 判定用圆心 | 按“红线 0 条 + 门禁全部达标”做出的发布结论 | 第 6.1 步的结论 |
| ⑤ 观测 | 复用圆心 | 线上流量上同一组评估器的分数、业务分诊报告 | CloudWatch Evaluations 页签、分诊报告 |
| ⑥ 回流 | 回灌圆心 | （本次没有做）线上失败样本带归因进入黄金集 | 后续版本 |

## 8.2 你走过的两条回路 {#s-8-2}

- **修评估体系**（第 2.4 步）：你们为一条“部分覆盖”的判据补了黄金样本（实测里是“哪怕看起来很小的缺陷也不能自动拒绝”这条红线），冻结了新版本。改的是尺子，所以之后所有的分数都以这一版为准。
- **修 Agent**（第 5 章）：Claude Code 根据评估结果改了提示词和工具；V0 和 V1 用同一把尺子量，对比页上的提升才可信。如果你的 V1 只有一条话术红线，你也看到了：门禁全过也不能发布。

## 8.3 还没做的一环：回流 {#s-8-3}

飞轮转完一圈，生产才是最有价值的输入：在线评估里打了低分、被业务方投诉的会话，带着“错在哪一维”的归因放回黄金集，下一轮评估就会盯住它，黄金标准越滚越硬。这一环会在后续版本的实验里展开。

## 8.4 三分钟复述 {#s-8-4}

试着用三分钟给同事讲清楚这次实验（可以对着对比页和分诊报告讲）：

1. **问题**：每月大量需求反馈，人工判断重要 / 紧急 / 是否迭代，拒绝话术难统一；
2. **标准**：鱼骨图里业务方确认的障碍 → 判据表 → 冻结的黄金集（含不可自动拒绝的红线）；
3. **评估**：V0 有几条红线、三项门禁各多少，主要错在哪一维；
4. **优化**：改了什么（口径 / 工具 / 红线 / 话术），V1 的结论；
5. **发布与观测**：发布结论，在线评估怎么持续盯住它，上个月 60 条的分诊结果。

## 检查一下：整个飞轮有没有对齐黄金标准？ {#s-8-check}

**从第 2 章到第 6 章，有没有哪一步用的不是同一个圆心？** 比如：评估用的黄金集不是冻结的那一版、对比的两次评估用了不同的评估器、在线评估的门禁和红线评估器和发布前评估的不一样。能一口气说出“全程是同一版黄金集、同一组评估器”，这一圈飞轮才算转稳了。
