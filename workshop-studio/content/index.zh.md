> **你在这里**：开场 · 六环全景（① 定义 → ② 构建 → ③ 评估 → ④ 发布 → ⑤ 观测 → ⑥ 回流 · 圆心：黄金标准）

**用时**：约 10 分钟

这是一个 2–3 小时的动手实验。你会把一个 Agent 从“能跑”推进到“有证据可以发布”：先和业务方一起定义什么是好，再部署、评估、优化，最后按同一套标准决定能不能发布，并在线上持续打分。全程只有一条主线：Agent 运行在 **Amazon Bedrock AgentCore Runtime** 上，用 **AgentCore Evaluations** 打分。所有数据都是合成的。

## 0.1 这个实验做什么 {#s-0-1}

:::alert{header="场景包：企业软件平台的需求评审（样例平台：示例 CRM PaaS，合成）" type="info"}
一家企业软件平台每月收到大量客户需求反馈。产品团队希望一个**需求反馈分诊 Agent** 先理解平台已有能力，再对每条反馈给出：

| 字段 | 取值 | 说明 |
|---|---|---|
| `important` 是否重要 | 是 / 否 | 影响面、客户价值、是否通用 |
| `urgent` 是否紧急 | 是 / 否 | 生产环境是否正在受影响、有无时间节点 |
| `decision` 处理建议 | 迭代 / 拒绝 / 待评估 | 判“拒绝”时必须写内部理由和给客户的话术 |
| `level` 优先级 | P0 / P1 / P2（预留） | 默认不启用，见扩展「标签方案切换」 |
| `reasoning` / `reject_reason` / `customer_reply` | 文本 | 判断依据 / 专业拒绝理由 / 对客户的沟通话术 |

业务方的目标：三项判断的准确率都**不低于 70%**，并且有几类需求**绝对不能被自动拒绝**（数据丢失、安全、合规、合同承诺、线上缺陷）。
:::

## 0.2 AgentDLC 六环飞轮 {#s-0-2}

AgentDLC（Agent Development Lifecycle）把 Agent 的生命周期画成一个**飞轮**而不是一条流水线：六个环首尾相接，生产不是终点，而是下一轮最有价值的输入。飞轮的**圆心是黄金标准**：一套版本化的黄金集，加一套五维（认知、质量、责任、成本、性能）判据。每一环都和圆心发生关系。

:image[AgentDLC 六环飞轮：六个环围绕圆心“黄金标准”，以及修 Agent 和修评估体系两条回路]{src="/static/images/flywheel-overview.svg" width=900 height=560}

*图 0-1 六环飞轮与两条回路*

| 环 | 和圆心的关系 | 在本实验里你做什么 | 章节 |
|---|---|---|---|
| ① 定义 | 产出圆心 | 和业务方画鱼骨图，把障碍翻译成判据，补黄金样本并冻结 | 第 2 章 |
| ② 构建 | 遵循圆心 | 把 V0 部署到 AgentCore Runtime，确认 trace 里带着要被打分的结论 | 第 3 章 |
| ③ 评估 | 取用圆心 | 注册评估器，用冻结的黄金集给 V0 打分，按三大支柱读结论、做归因 | 第 4 章 |
| ②③ 再走一圈 | 遵循 + 取用 | 用 Claude Code 根据评估结果写出你的 V1，重新部署、再评估、对比 | 第 5 章 |
| ④ 发布 | 判定用圆心 | 按“红线 0 条 + 门禁全部达标”决定能不能发布 | 第 6 章 |
| ⑤ 观测 | 复用圆心 | 在线评估用同一组评估器给新流量打分，生成业务分诊报告 | 第 6 章 |
| ⑥ 回流 | 回灌圆心 | 把线上失败样本带归因放回黄金集（本次实验不展开，见第 8 章） | — |

几个贯穿全程的词：

| 词 | 意思 | 第一次动手 |
|---|---|---|
| 黄金集 | 一组带标准答案的样例（每条需求的期望标签、拒绝要点、话术要点、标注理由）；冻结后成为“尺子” | 2.1、2.4 |
| 判据 | 一条可以打分的要求：主语是 Agent，谓语能在输出或 trace 上观察到；每条分到三档之一 | 2.3 |
| 红线 / 门禁 / 观测 | 判据的三档，也是评估结论的“三大支柱”：红线一票否决、门禁全部达标才放行、观测只看趋势 | 2.3、4.6 |
| session / trace / span | Agent 处理一条需求 = 一个 session；它在 CloudWatch 里留下一条 trace（调用链），trace 由一个个 span（每一步调用）组成；评估器读的就是这些 | 3.1、3.4 |

守住飞轮只有一条纪律：**每一环结束时都问一句“这一环有没有对齐黄金标准？”**。所以每一章最后都有一个这样的检查问题。

## 0.3 两条回路：修评估体系，还是修 Agent {#s-0-3}

评估不达标时，先判断问题出在哪一边，再动手：

| 回路 | 改什么 | 什么时候走 | 改完要做什么 |
|---|---|---|---|
| **修 Agent** | 提示词、工具、模型 | Agent 拿到了足够的信息和规则，却没有用对 | 重新部署 Agent，用**同一份**黄金集和评估器再评估，前后分数才可比 |
| **修评估体系** | 黄金集、能力目录、判据 | Agent 按它拿到的信息做得没错，是标准或数据本身不完整（等于在改尺子） | 冻结新黄金集、重新部署评估器；改过尺子之后，旧分数要按新尺子重新算基线 |

第 2 章补黄金样本是在**修评估体系**；第 5 章改提示词和工具是在**修 Agent**。第 5 章优化时不要顺手改黄金集或评估器，否则 V0 和 V1 的分数不能比。

## 0.5 你的角色 {#s-0-5}

:::alert{header="场景包：角色卡" type="info"}
第 2 章画鱼骨图时，你们小组扮演**业务方**：平台产品部的需求评审小组（一名产品总监拍板，两名产品经理逐条评审，一名客户成功负责人把拒绝话术发给客户）。每月一次评审会，处理上个月的需求反馈；你们为“什么算评审得好”签字。

完整角色卡在实验环境里的 `data/scenario/role-card.md`（第 2.1 步会打开它）。卡里没写的，就回答“不知道”或“没有”，不要现编数字。
:::

## 0.6 版本命名 {#s-0-6}

| 名称 | 文件 | 是什么 |
|---|---|---|
| **V0** | `agent/adlc_agent/prompts/v0.md` + 工具 `lookup_capability` | 故意偏弱的基线，第 3 章部署、第 4 章评估 |
| **V1** | `agent/adlc_agent/prompts/v1.md`（你在 5.2 生成） | 你们自己的第一轮优化：Claude Code 读第 4 章的评估结果后写出 |
| **V1 参考版** | `agent/adlc_agent/prompts/v1-ref.md` + 工具 `search_capabilities`、`find_similar_requests` | 实验准备好的参考答案，时间不够时用它代替你的 V1 |
| V2 | — | 预留给后续的回流环节 |

切换版本是两条命令：`./50-switch-version.sh v1`（或 `v1-ref`、`v0`）改配置，再 `./30-deploy-runtime.sh` 重新部署，见第 5.3 步。部署输出里的“Runtime 版本 1、2、3……”只是部署次数的计数，和 V0 / V1 无关。实验里的 Agent 是一个用 Strands Agents 写的 mock agent（需求分诊 Agent），扩展页里说的“mock agent”就是它。

## 0.7 实验环境长什么样 {#s-0-7}

- 每位学员一个 AWS 账号（Workshop Studio 准备好的），区域 us-west-2（或讲师指定的 us-east-1）。
- 一台实验 EC2（Amazon Linux 2023），**只能**通过 Session Manager 登录，没有任何入站端口。实验材料已经由 CloudFormation 从 Workshop Studio 的资产桶下载并解压到 `~/adlc-lab`，工具（Python 3.12 + uv、Node.js、Claude Code、AWS CLI）都装好了。所有命令都在这台 EC2 上执行，笔记本只用来看手册和 AWS 控制台。
- 脚本编号的十位数就是章号：`10-check-env.sh` 在第 1 章，`30-deploy-runtime.sh` 在第 3 章，`4x` 在第 4 章，以此类推；后面的章节会重新运行前面的脚本。`ext-*.sh` 只在扩展里用。`00-config.sh` 是被其它脚本加载的共用配置，不是步骤；`tools/` 下是辅助脚本；`data/prompts/` 里给 Claude Code 的提示词有自己的编号，和章号无关。
- 数据流：Agent 在 AgentCore Runtime 上运行，trace 自动进入 CloudWatch（`aws/spans`），AgentCore Evaluations 从 CloudWatch 读取 trace 并按黄金集打分；结果页面放在你自己的私有 S3 桶里，在控制台里打开。
